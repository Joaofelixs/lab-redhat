O que foi validado

O HML está em 4.18.56, arquitetura ARM64, plataforma AWS. Seu node está Ready, os MCPs estão Updated e não estão Degraded ou Updating. Os operadores estão disponíveis, sem degradação, e sem Upgradeable=False na consulta inicial. Ele é SNO; o reboot interrompe temporariamente suas aplicações. O Interconnect do HML conecta ao cluster PROD, que deve permanecer disponível durante o teste.

O grafo oficial ARM64 em stable-4.19 anuncia 4.18.56 → 4.19.55. O salto 4.19.55 → 4.20.46 aparece no conjunto de atualizações condicionais com o risco VSphereConfigCloudControllerCrash. O HML usa AWS, mas a decisão final deve ser reavaliada pelo CVO depois da etapa 4.19. Não force nem ignore precondições.

O ConfigMap admin-acks do HML estava vazio. Nenhum reconhecimento foi gravado automaticamente. Antes de executar, revise as APIs removidas de cada transição e os bloqueios apresentados pelo CVO. Confirme backup/recuperação, compatibilidade dos operadores e a janela de manutenção; esses itens não foram aprovados pelo simples fato de o TALM estar instalado.

Como a seleção foi limitada

Um administrador vinculou o ManagedClusterSet hml ao namespace talm-upgrades. Esse vínculo permite que o Placement enxergue o conjunto; não inicia upgrade. O Placement e os dois CGUs exigem conjuntamente:

name: cluster-2dns8
cluster.open-cluster-management.io/clusterset: hml
vendor: OpenShift
upgrades.lab-redhat.io/campaign: ocp-4-20-46
upgrades.lab-redhat.io/engine: talm

O PlacementDecision foi conferido: somente cluster-2dns8. As policies de upgrade não foram propagadas para cluster-xgdnd. A label de campanha não é uma aprovação. O ClusterSet sozinho também não define ordem nem concorrência.

Policies e campanhas

As duas policies, tanto o recurso raiz quanto a ConfigurationPolicy interna, usam remediationAction: inform. NonCompliant é esperado: o HML ainda está na versão de origem. Isso não significa falha de conectividade nem autorização para aplicar a versão. O TALM exigiu upstream, channel e version para resolver a release sem image explícita; upstream foi incluído nos manifests.

fleet-4-19-55
  enable: false
  policy: talm-upgrade-4-19-55
  destino: cluster-2dns8

fleet-4-20-46
  enable: false
  policy: talm-upgrade-4-20-46
  blockingCRs: fleet-4-19-55
  destino: cluster-2dns8

Ambas usam canaries: [cluster-2dns8], maxConcurrency: 1, timeout: 240 minutos, batchTimeoutAction: abort, backup: false e preCaching: false. Nenhuma deve ter status.status.startedAt preenchido enquanto aguarda autorização.

Particularidade: CGUs automáticos do ZTP

Ao instalar o TALM, seu controlador ManagedClusterForCGU criou registros iniciais em ztp-install para os clusters já existentes. Esses registros não tinham managedPolicies e foram imediatamente concluídos sem atualização. Foram inspecionados e colocados em enable: false. Não são as campanhas de upgrade, que ficam em talm-upgrades. O controlador também acrescentou a label ztp-done. Não confunda esse marcador de inicialização com uma versão atualizada.

Argo CD e a autorização futura

As Applications talm-upgrade-policies e talm-upgrade-campaigns usam o Git como fonte e têm Auto Sync, prune e selfHeal desligados. As policies observacionais e campanhas desabilitadas foram preparadas administrativamente, antes de criar as Applications. Depois foi feita uma sincronização inicial somente desses recursos: ambas ficaram Synced, com operação Succeeded. Os dois CGUs passaram a validação (Validated=True), ficaram em NotEnabled e sem startedAt. Essa sincronização de preparação não aprovou upgrade. Não foram criados hooks que habilitam campanhas.

Não faça alterações para enable: true agora. Em uma janela autorizada, após as revisões pendentes, alterar os dois CGUs para enable: true no Git e sincronizar a Application de campanhas permite a sequência automática: a etapa 4.20 aguarda Succeeded da etapa 4.19. Se quiser revisar antes do segundo salto, habilite somente o primeiro. Uma dependência ordena etapas, mas não corrige uma release inelegível ou um admin-ack pendente.
