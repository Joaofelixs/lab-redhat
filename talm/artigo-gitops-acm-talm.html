Do Git ao upgrade: OpenShift com Argo CD, ACM e TALM

Atualização de 14/11/2026: o TALM 4.20.5 foi instalado e o piloto HML está em preparação, sem autorização de upgrade. Este artigo conserva o roteiro didático original; para o estado atual, seleção do ClusterSet hml e comandos aplicáveis ao laboratório, use o guia do piloto HML e os YAMLs atuais do Git.

Um guia do laboratório para entender, publicar e preparar uma campanha de atualização de clusters. Os exemplos YAML abaixo são extraídos dos arquivos versionados neste repositório, não de um ambiente supostamente instalado.

Estado deste trabalho: arquivos preparados e validados localmente. Não instalamos o TALM, não criamos estas Applications no cluster e não iniciamos uma campanha. Os comandos de aplicação são um roteiro para uma futura janela autorizada, não ações já executadas.

1. Entenda antes de executar

Imagine cinco clusters de lojas. Você quer atualizar primeiro uma loja piloto, verificar o resultado e depois atender as demais sem interromper todas ao mesmo tempo. O Git registra o plano; o TALM organiza sua execução. Esse controle não transforma um caminho de atualização incompatível em um caminho seguro.

ComponenteO que faz e por que existe
Git e GitHubGit registra alterações locais; GitHub hospeda o repositório remoto. Commit registra uma revisão; push publica essa revisão.
Argo CDLê o repositório e compara os manifests com o cluster. Refresh atualiza essa comparação; Sync aplica a configuração.
ACMGerencia os clusters e distribui policies. O hub é a central; os spokes são os destinos gerenciados.
Policy e conformidadeUma regra descreve o resultado desejado. Compliant significa que as verificações declaradas foram satisfeitas; NonCompliant indica diferenças.
PlacementEscolhe em quais clusters as policies são observadas. Não define concorrência de upgrade.
TALM e CGUO operador TALM coordena o plano descrito no ClusterGroupUpgrade: seleção, pilotos, lotes, dependências e timeout.
CVOO Cluster Version Operator de cada OpenShift executa a atualização da plataforma.
Git local → commit → push → GitHub
                              ↓ leitura
                           Argo CD
                              ↓ Sync aprovado
             policies ACM + ClusterGroupUpgrade no HUB
                              ↓ TALM coordena os lotes
                  CVO de cada cluster → atualização

As Applications deste guia apontam para a API do próprio hub. Não precisam cadastrar cada spoke como destino do Argo CD: o ACM distribui a configuração. Um namespace separa os recursos de gerenciamento; ele não é outro cluster.

2. Conheça as pastas e os limites de segurança

talm/
  operator/       Subscription do operador; aprovação manual
  bootstrap/      namespace, vínculo infra, projeto e permissões
  policies/       seleção e versões desejadas, sempre em inform
  campaigns/      CGUs 4.19.55 e 4.20.46, enable: false
  applications/   duas Applications, Auto Sync desligado

Não há Kustomization na raiz talm. Isso impede tratar todas as etapas como um único pacote indistinto. O fluxo anterior ClusterCurator, em gitops-upgrades e upgrades/ocp, não é convertido nem desativado por estes arquivos.

Não execute os dois mecanismos no mesmo cluster simultaneamente. A label engine=talm apenas seleciona este fluxo; ela não cancela um curator. Aguarde operações anteriores terminarem antes de migrar um destino.

O próprio hub está excluído. Um hub SNO reiniciado interrompe o coordenador, a console e o Argo CD. Para aprender a coordenação da frota, use um spoke externo.

3. Publique os arquivos no Git

Trabalhe na cópia já existente do repositório. Se começar em outra máquina, clone o projeto e entre na pasta. Não crie um repositório dentro de outro.

git clone https://github.com/Joaofelixs/lab-redhat.git
cd lab-redhat
git status --short

Se já está em /home/joao/Documentos/lab-redhat, não clone novamente. O status mostra alterações locais. Depois de editar e validar os arquivos, publique somente os arquivos revisados, sem incluir kubeconfigs, tokens ou senhas:

git diff -- talm/
git add talm/
git diff --cached --check
git diff --cached --stat
git commit -m "Prepare TALM fleet upgrade campaign"
git push origin main

Em uma equipe, prefira uma branch e um pull request com revisão antes do merge. Um push não aplica recursos sozinho: a Application precisa existir e, neste projeto, todas as sincronizações são manuais.

4. Confira os pré-requisitos

Você precisa de um hub com ACM, OpenShift GitOps e acesso administrativo para o bootstrap; pelo menos um spoke importado e saudável; o ClusterSet infra; acesso às imagens e às versões de atualização. Confirme compatibilidade entre ACM, TALM, versão do hub, spokes e operadores antes de instalar.

# No hub: somente consulta
oc whoami --show-server
oc get managedclusters --show-labels
oc get managedclusterset infra
oc get clustercurators -A
oc get multiclusterhub -A
oc get argocds.argoproj.io -A

# Em cada destino, usando seu contexto correto
oc get clusterversion version
oc adm upgrade
oc get co
oc get nodes
oc get mcp

Antes de aprovar, os operadores, nodes e pools precisam estar saudáveis e os backups devem ser recuperáveis. Valide também aplicações, capacidade e janela de manutenção. Não use force para ignorar risco ou caminho não recomendado.

4.19.55 e 4.20.46 são as versões propostas, não uma garantia de elegibilidade. O salto para 4.20.46 teve risco condicional de vSphere na consulta do lab. Confirme novamente o grafo e a avaliação do CVO de cada destino. Se o destino já está em 4.19 ou posterior, não execute cegamente a etapa intermediária.

5. Instale o operador, somente quando autorizado

Um operador é um controller especializado. Instalar a Subscription disponibiliza o TALM; ainda não autoriza um upgrade da frota. O canal 4.18 está fixado no exemplo para evitar seguir automaticamente outro minor, mas deve ser reavaliado para a versão real do hub. O código usa aprovação manual de InstallPlan.

Arquivo: talm/operator/subscription.yaml

apiVersion: operators.coreos.com/v1alpha1
kind: Subscription
metadata:
  name: topology-aware-lifecycle-manager
  namespace: openshift-operators
spec:
  channel: "4.18"
  name: topology-aware-lifecycle-manager
  source: redhat-operators
  sourceNamespace: openshift-marketplace
  installPlanApproval: Manual

# ETAPA DE INSTALAÇÃO FUTURA: modifica o hub
oc apply -k talm/operator/
oc get subscription topology-aware-lifecycle-manager -n openshift-operators
oc get installplan -n openshift-operators
oc get csv -n openshift-operators

Inspecione o InstallPlan associado a esta Subscription e aprove somente esse plano. O namespace pode conter planos de outros operadores: não aprove todos.

oc get subscription topology-aware-lifecycle-manager -n openshift-operators   -o jsonpath='{.status.installPlanRef.name}{"\n"}'
# Substitua o nome abaixo pelo plano inspecionado e aprovado.
oc get installplan NOME_DO_PLANO -n openshift-operators -o yaml
oc patch installplan NOME_DO_PLANO -n openshift-operators   --type=merge -p '{"spec":{"approved":true}}'
oc wait crd/clustergroupupgrades.ran.openshift.io   --for=condition=Established --timeout=120s
oc rollout status deployment/cluster-group-upgrades-controller-manager   -n openshift-operators --timeout=180s

A CRD ensina à API o que é ClusterGroupUpgrade. Sem ela, o sync de campanhas falha com no matches for kind. Antes de avançar, confirme também CSV Succeeded.

6. Prepare namespace, ClusterSet, projeto e RBAC

O bootstrap é uma tarefa administrativa separada. O namespace talm-upgrades guarda policies e campanhas no hub. Crie-o antes dos recursos namespaced:

Arquivo: talm/bootstrap/namespace.yaml

apiVersion: v1
kind: Namespace
metadata:
  name: talm-upgrades
  annotations:
    argocd.argoproj.io/sync-wave: "-10"

# Modifica o hub; execute apenas na preparação aprovada.
oc apply -f talm/bootstrap/namespace.yaml
oc wait namespace/talm-upgrades --for=jsonpath='{.status.phase}'=Active --timeout=60s
oc apply -k talm/bootstrap/

O ManagedClusterSetBinding permite ao Placement desse namespace selecionar clusters do conjunto infra. Criar esse vínculo exige a permissão especial managedclustersets/bind. Por isso ele fica no bootstrap do administrador, não na Application de policies. Não concedemos essa permissão global ao Argo CD.

Arquivo: talm/bootstrap/cluster-set-binding.yaml

apiVersion: cluster.open-cluster-management.io/v1beta2
kind: ManagedClusterSetBinding
metadata:
  name: infra
  namespace: talm-upgrades
spec:
  clusterSet: infra
AppProject: repositório, destino e tipos de recurso permitidos

Arquivo: talm/bootstrap/project.yaml

apiVersion: argoproj.io/v1alpha1
kind: AppProject
metadata:
  name: talm-upgrades
  namespace: openshift-gitops
spec:
  description: Policies inform e campanhas TALM com aprovacao explicita
  sourceRepos:
  - https://github.com/Joaofelixs/lab-redhat.git
  destinations:
  - server: https://kubernetes.default.svc
    namespace: talm-upgrades
  clusterResourceWhitelist: []
  namespaceResourceWhitelist:
  - group: policy.open-cluster-management.io
    kind: Policy
  - group: policy.open-cluster-management.io
    kind: PlacementBinding
  - group: cluster.open-cluster-management.io
    kind: Placement
  - group: ran.openshift.io
    kind: ClusterGroupUpgrade

AppProject é uma barreira do Argo CD. RBAC é a autorização da API Kubernetes. Uma configuração não substitui a outra. A Role abaixo permite somente os tipos necessários dentro de talm-upgrades; não concede cluster-admin nem delete.

Role e RoleBinding do application-controller

Arquivo: talm/bootstrap/rbac.yaml

apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  name: argocd-talm-upgrades
  namespace: talm-upgrades
rules:
- apiGroups:
  - policy.open-cluster-management.io
  resources:
  - policies
  - placementbindings
  verbs: [get, list, watch, create, update, patch]
- apiGroups:
  - cluster.open-cluster-management.io
  resources:
  - placements
  verbs: [get, list, watch, create, update, patch]
- apiGroups:
  - ran.openshift.io
  resources:
  - clustergroupupgrades
  verbs: [get, list, watch, create, update, patch]
---
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  name: argocd-talm-upgrades
  namespace: talm-upgrades
subjects:
- kind: ServiceAccount
  name: openshift-gitops-argocd-application-controller
  namespace: openshift-gitops
roleRef:
  apiGroup: rbac.authorization.k8s.io
  kind: Role
  name: argocd-talm-upgrades

oc auth can-i create policies.policy.open-cluster-management.io   -n talm-upgrades   --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller
oc auth can-i create clustergroupupgrades.ran.openshift.io   -n talm-upgrades   --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller

Se sua instância Argo CD usa outro namespace ou ServiceAccount, ajuste o RoleBinding antes de aplicar. As permissões listadas são de gerenciamento no hub; os agentes do ACM precisam também estar autorizados e saudáveis nos destinos.

7. Conecte o repositório ao Argo CD

Acesse o Argo CD e entre pelo RHBK, usando uma identidade autorizada a gerenciar o projeto. No lab, o endereço configurado foi:

Argo CD do laboratório.

Em Settings → Repositories → Connect Repo, selecione Git/HTTPS e informe https://github.com/Joaofelixs/lab-redhat.git. Para um repositório público, não é necessário fornecer senha. Para um privado, use uma credencial somente de leitura desse repositório ou uma deploy key; não reutilize um token administrador.

A autenticação do usuário pelo RHBK não autentica o repo-server no GitHub. São conexões diferentes. Confirme Connection Status: Successful e mantenha a validação TLS habilitada. Não desative validação de certificado para resolver um problema de confiança; disponibilize a CA correta quando necessário.

O Argo CD armazena suas credenciais Git em Secrets. Não versione um token em um Secret YAML: base64 não é criptografia. Se optar por gestão declarativa de credenciais, use um gerenciador apropriado, como External Secrets ou Sealed Secrets.

8. Cadastre as duas Applications

Separe a intenção de versão da autorização de execução. Uma Application gerencia as policies em inform; a outra gerencia os CGUs desativados. Ambas apontam para o hub e têm Auto Sync, prune e selfHeal desligados.

Application das policies: path talm/policies

Arquivo: talm/applications/policies.yaml

# Reference only: create this Application separately when TALM is installed.
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: talm-upgrade-policies
  namespace: openshift-gitops
spec:
  project: talm-upgrades
  source:
    repoURL: https://github.com/Joaofelixs/lab-redhat.git
    targetRevision: main
    path: talm/policies
  destination:
    server: https://kubernetes.default.svc
    namespace: talm-upgrades
  syncPolicy:
    automated:
      enabled: false
      prune: false
      selfHeal: false
Application das campanhas: path talm/campaigns

Arquivo: talm/applications/campaigns.yaml

# Reference only: create this Application separately when TALM is installed.
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: talm-upgrade-campaigns
  namespace: openshift-gitops
spec:
  project: talm-upgrades
  source:
    repoURL: https://github.com/Joaofelixs/lab-redhat.git
    targetRevision: main
    path: talm/campaigns
  destination:
    server: https://kubernetes.default.svc
    namespace: talm-upgrades

      enabled: false
      prune: false
      selfHeal: false

# Só cadastra as Applications; não faz Sync.
oc apply -k talm/applications/
oc get applications.argoproj.io -n openshift-gitops

Você também pode cadastrar essas configurações pela interface Argo CD ou pelo ACM integrado ao GitOps. Mantenha o projeto talm-upgrades, os paths e os destinos dos YAMLs. Não crie um segundo ApplicationSet gerenciando os mesmos objetos e deixe Auto Sync desmarcado. Não aponte uma Application com recursão para a raiz talm: bootstrap, operador e campanhas têm responsabilidades diferentes.

Uma Application pode aparecer OutOfSync/Missing antes do primeiro Sync; isso é esperado. ComparisonError ou acesso negado ao Git precisam ser corrigidos.

9. Distribua as policies sem executar upgrades

Faça Refresh e revise o diff de talm-upgrade-policies. Depois do bootstrap e da instalação do operador, sincronize somente essa Application. Ela cria um Placement, um PlacementBinding e duas policies em inform. Não solicita alteração imediata de versão. O vínculo infra já foi preparado pelo administrador.

Seleção e associação das policies

Arquivo: talm/policies/selection.yaml

  - infra

10. Selecione um spoke e defina o canário

Exemplo para um ManagedCluster externo já importado, chamado cluster-dev. Troque esse nome pelo real. Verifique se o cluster já pertence a outro ClusterSet antes de mudar sua associação; mover de conjunto afeta outros Placements.

# Consulta no hub, sem alterar o cluster de destino.
oc get managedcluster cluster-dev --show-labels
oc get managedclusteraddons -n cluster-dev

# Seleção FUTURA aprovada: modifica as labels do cadastro no hub.
oc label managedcluster cluster-dev   cluster.open-cluster-management.io/clusterset=infra   upgrades.lab-redhat.io/campaign=ocp-4-20-46   upgrades.lab-redhat.io/engine=talm --overwrite

A seleção exige vendor=OpenShift, normalmente publicada pelo cadastro de distribuição. Não altere esse indicador para mascarar um tipo diferente de cluster. A exclusão local-cluster=true mantém o hub fora da campanha.

Edite canaries em ambos os CGUs e publique a escolha no Git. Um canário precisa estar dentro da seleção; listá-lo ali não basta para selecioná-lo:

remediationStrategy:
  canaries:
  - cluster-dev
  maxConcurrency: 1
  timeout: 240

Depois confira a distribuição e espere as policies reportarem estado para os destinos. Antes de atualizar, NonCompliant por versão divergente é esperado. Ausência de status, TemplateError ou agentes indisponíveis não são prontidão.

oc get placementdecisions -n talm-upgrades -o yaml
oc get policies.policy.open-cluster-management.io -n talm-upgrades
oc get policies.policy.open-cluster-management.io -n cluster-dev

11. Prepare e aprove a campanha na hora certa

Primeiro, sincronize talm-upgrade-campaigns com enable: false nos dois CGUs. Isso permite inspecionar a seleção e o plano antes de autorizar a remediação. Neste exemplo preCaching também está false, portanto não preparamos downloads.

Primeira etapa: fleet-4-19-55

Arquivo: talm/campaigns/01-upgrade-4-19-55.yaml

apiVersion: ran.openshift.io/v1alpha1
kind: ClusterGroupUpgrade
metadata:
  name: fleet-4-19-55
  namespace: talm-upgrades
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
spec:
  enable: false
  preCaching: false
  clusterLabelSelectors:
  - matchLabels:
      vendor: OpenShift
      upgrades.lab-redhat.io/campaign: ocp-4-20-46
      upgrades.lab-redhat.io/engine: talm
    matchExpressions:
    - key: local-cluster
      operator: NotIn
      values: ["true"]
  managedPolicies:
  - talm-upgrade-4-19-55
  remediationStrategy:
    # Set explicit canary names here after importing and validating spokes.
    canaries: []
    maxConcurrency: 1
    timeout: 240
  batchTimeoutAction: abort
Segunda etapa: fleet-4-20-46

Arquivo: talm/campaigns/02-upgrade-4-20-46.yaml

apiVersion: ran.openshift.io/v1alpha1
kind: ClusterGroupUpgrade
metadata:
  name: fleet-4-20-46
  namespace: talm-upgrades
  annotations:
    argocd.argoproj.io/sync-options: Prune=false
spec:
  enable: false
  preCaching: false
  blockingCRs:
  - name: fleet-4-19-55
    namespace: talm-upgrades
  clusterLabelSelectors:
  - matchLabels:
      vendor: OpenShift
      upgrades.lab-redhat.io/campaign: ocp-4-20-46
      upgrades.lab-redhat.io/engine: talm
    matchExpressions:
    - key: local-cluster
      operator: NotIn
      values: ["true"]
  managedPolicies:
  - talm-upgrade-4-20-46
  remediationStrategy:
    canaries: []
    maxConcurrency: 1
    timeout: 240
  batchTimeoutAction: abort

Para uma aprovação por salto, mude apenas o primeiro enable para true no Git, faça commit/push e, na janela combinada, execute Sync da Application de campanhas. Após validar a conclusão da 4.19, aprove a segunda etapa da mesma forma.

Para uma aprovação única da sequência, os dois enable podem ser aprovados no mesmo commit. A segunda etapa continua bloqueada por blockingCRs até a primeira concluir com sucesso. Isso termina a etapa 4.19 na frota selecionada antes de iniciar a 4.20; não termina os dois saltos de cada cluster antes do próximo.

# Depois de editar os enable e revisar os participantes:
git diff -- talm/campaigns/
git add talm/campaigns/
git commit -m "Approve TALM upgrade maintenance window"
git push origin main

# CLI Argo CD autenticada, alternativa ao botão Sync:
argocd app diff talm-upgrade-campaigns
argocd app sync talm-upgrade-campaigns

Aqui está a autorização disruptiva: Sync com enable: true permite ao TALM remediar. Push sozinho não inicia porque Auto Sync está desligado. Uma vez habilitada a sequência, você não precisa sincronizar uma Application para cada spoke: o TALM coordena os lotes.

Não altere a policy raiz para enforce. Não use uma label batch como substituto do limite de concorrência. Sync waves do Argo CD não substituem blockingCRs nem a observação da conclusão de um upgrade.

12. Acompanhe até a conclusão real

# No hub:
oc get clustergroupupgrades.ran.openshift.io -n talm-upgrades
oc describe clustergroupupgrade fleet-4-19-55 -n talm-upgrades
oc get clustergroupupgrade fleet-4-19-55 -n talm-upgrades   -o jsonpath='{.status.remediationPlan}{"\n"}{.status.conditions}{"\n"}'
oc get policies.policy.open-cluster-management.io -A

# No spoke, usando seu contexto/kubeconfig:
oc get clusterversion version
oc get co
oc get nodes
oc get mcp

Synced significa que o Argo CD aplicou o plano. Succeeded no CGU significa que as verificações das policies da campanha foram satisfeitas. Confirme também o estado dos clusters e os testes de aplicação. Não interprete a falta de jobs ClusterCurator como erro: TALM usa outro mecanismo de coordenação.

Mantenha a seleção estável durante a execução. Ao concluir, registre resultados e arquive a campanha com cuidado. Crie novos nomes de CGU para uma campanha nova. A policy intermediária pode voltar a NonCompliant quando o cluster chega à 4.20; isso não autoriza reaplicá-la em enforce nem tentar retornar à 4.19.

Uma reversão de commit não é downgrade do OpenShift. O backup descrito em artigos históricos para SNO não equivale a restauração automática de todos os PVCs. Defina e teste o procedimento de recuperação antes de aprovar upgrades.

14. O que está pronto e o que falta provar

  • Pronto no Git: Subscription, bootstrap, RBAC limitado, policies em inform, seleção, CGUs dependentes e Applications manuais.
  • Validação local: renderização Kustomize, consistência das referências e, quando disponível, schema de CGU compatível.
  • Ainda não comprovado por este trabalho: instalação do operador, admissão dos recursos no seu hub e execução ponta a ponta em um spoke piloto.
  • Fora do escopo automático: escolha segura de versão, backup/restauração, testes de negócio, preparação do registry espelho e avaliação de riscos.

Não declare o ambiente funcional apenas porque os YAMLs existem. Considere-o operacional quando repositório, permissões, operador, agentes, policies e CGUs forem validados e uma campanha piloto autorizada concluir com sucesso.
