Upgrade de clusters OpenShift com GitOps e ACM

Este fluxo guarda no Git a intencao de atualizar clusters. Ele usa o Argo CD para criar recursos ClusterCurator no hub ACM. O ClusterCurator solicita e acompanha a atualizacao; o Cluster Version Operator de cada OpenShift executa o upgrade.

Estado configurado: local-cluster selecionado como piloto, mas com sincronizacao automatica explicitamente desativada. A campanha proposta passa por 4.19.55 e termina em 4.20.46. Registrar essas versoes no Git nao aprova nem inicia a atualizacao.

1. Entender os componentes

  • Hub: cluster onde o ACM gerencia os outros clusters.
  • ManagedCluster: cadastro de um cluster no ACM. Seu nome identifica tambem o namespace correspondente no hub.
  • ApplicationSet: gera uma Application Argo CD por entrada na lista aprovada. A lista vazia nao gera aplicacoes.
  • Application: aplica o ClusterCurator no namespace do cluster gerenciado, mas sempre na API do hub.
  • ClusterCurator: recurso que coordena a operacao de upgrade.
  • Lote: grupo operacional, como piloto ou homologacao. A label batch identifica o lote; ela nao implementa uma fila automatica.
Git → Argo CD → ClusterCurator no hub → cluster gerenciado → CVO → nodes

Esses recursos nao ficam em policies-acm: esse namespace guarda policies de governanca. Cada ClusterCurator fica no namespace do respectivo ManagedCluster e precisa ter o mesmo metadata.name do cluster. No piloto, nome e namespace sao local-cluster. O ApplicationSet ajusta ambos por destino. A versao fica em spec.upgrade, nao no nome do recurso. Caso contrario, o controller procura um ManagedClusterInfo com o nome errado e ignora o upgrade.

2. Validar antes de aprovar

Em cada cluster de destino, confirme a versao e o caminho de atualizacao:

oc get clusterversion version
oc adm upgrade
oc get co
oc get nodes
oc get mcp

Exija nodes Ready, operators disponiveis e sem degradacao, MCPs atualizados, backup de etcd e dados das aplicacoes, compatibilidade de operadores e janela de manutencao. Investigue antes qualquer timeout recorrente de API/etcd. Nao use force ou allowExplicitUpgrade para contornar o caminho suportado.

No hub, confira o cadastro e a saude dos agentes:

oc get managedclusters
oc get managedclusteraddons -n NOME_DO_CLUSTER
oc get clustercurators -A

Um cluster importado precisa estar aceito, conectado e com seus agentes de gerenciamento saudaveis. Confira tambem se ja existe um ClusterCurator no mesmo namespace; nao execute campanhas concorrentes para o mesmo cluster.

3. Instalar a estrutura, sem iniciar upgrades

oc apply -k gitops-upgrades/
oc get applicationset ocp-upgrades -n openshift-gitops
oc get applications -n openshift-gitops -l upgrades.lab-redhat.io/batch

O primeiro comando cria o projeto restrito, o ApplicationSet e gera a Application upgrade-local-cluster, que aguarda Sync manual. O projeto permite somente ClusterCurator nos namespaces do hub, nao Deployments ou ClusterRoleBindings. Nenhuma atualizacao e disparada ao criar a Application. Para nao gerar nenhuma Application, use elements: [] no generator. A instancia Argo CD deve ter permissao para gerenciar ClusterCurator nesses namespaces; AppProject restringe operacoes, mas nao concede RBAC Kubernetes.

O arquivo gitops-upgrades/00-rbac-local-cluster.yaml concede ao ServiceAccount openshift-gitops-argocd-application-controller, de openshift-gitops, somente get, list, watch, create, update e patch de ClusterCurator no namespace local-cluster. Nao concede cluster-admin nem permissao de delete. Isso resolve o erro forbidden ao aplicar a campanha sem ampliar acesso a outros recursos.

oc auth can-i create clustercurators.cluster.open-cluster-management.io \
  -n local-cluster \
  --as=system:serviceaccount:openshift-gitops:openshift-gitops-argocd-application-controller

Para adicionar outros clusters, provisione uma Role e um RoleBinding equivalentes em cada namespace de ManagedCluster no hub, antes do Sync da campanha. Ajuste o ServiceAccount se usar outra instancia Argo CD. Nao use um ClusterRoleBinding amplo para contornar esse requisito. Aplicar o RBAC nao inicia o upgrade; a Application continua com sincronizacao manual.

4. Escolher versao e piloto no Git

Edite upgrades/ocp/cluster-curator.yaml: ajuste desiredUpdate, intermediateUpdate, e channel. Mantenha metadata.name igual ao nome do ManagedCluster, sem colocar a versao no nome. Nao reutilize cegamente a versao candidata para toda a frota: ela precisa estar disponivel no caminho suportado de cada cluster selecionado.

spec:
  desiredCuration: upgrade
  upgrade:
    channel: stable-4.20
    desiredUpdate: 4.20.46
    monitorTimeout: 180

Estado da campanha em 14/11/2026: a versao 4.19.55 foi concluida. O manifesto atual solicita somente 4.19.55 → 4.20.46 e nao possui intermediateUpdate. Nao aplique esta campanha em clusters ainda na 4.18.

intermediateUpdate e a versao completa da etapa intermediaria; desiredUpdate e o destino final. Neste lab, a versao de origem verificada foi 4.18.42: o fluxo proposto e 4.18.42 → 4.19.55 → 4.20.46. Essa configuracao solicita a sequencia automatica; nao existe uma aprovacao manual entre os saltos. Para revisar a 4.19 antes de continuar, crie duas campanhas separadas, primeiro com desiredUpdate: 4.19.55 e channel: stable-4.19, sem intermediateUpdate, e depois com desiredUpdate: 4.20.46 e channel: stable-4.20, tambem sem intermediateUpdate.

Consulta ao grafo em 13/11/2026, arquitetura amd64: stable-4.19 anunciou o salto 4.18.42 → 4.19.55. O salto 4.19.55 → 4.20.46 apareceu como condicional, com risco VSphereConfigCloudControllerCrash. Nao foi considerado um salto incondicionalmente recomendado. O CVO de cada cluster precisa avaliar a condicao de risco, a plataforma e os demais pre-requisitos. O lab usa plataforma None, mas isso nao dispensa a avaliacao. Nao use force para ignorar a condicao. O grafo e dinamico; consulte novamente no momento da aprovacao. A disponibilidade do primeiro salto em stable-4.19 nao garante que o curator conseguira resolver toda a sequencia com o canal stable-4.20: confira o caminho no canal da campanha antes de sincronizar.

Em gitops-upgrades/01-applicationset.yaml, a lista ja inclui local-cluster como piloto. Para adicionar outro destino, use seu nome ManagedCluster. Exemplo ilustrativo, nao um cluster existente:

elements:
- cluster: cluster-dev-01
  batch: piloto

Faca commit e push das alteracoes aprovadas e reaplique a estrutura caso ela ainda nao seja gerenciada por uma Application de bootstrap:

oc apply -k gitops-upgrades/

O ApplicationSet le a lista do seu recurso no hub, nao diretamente do arquivo no Git. Por isso e necessario reconciliar essa estrutura apos mudar a lista.

O piloto local-cluster e o proprio hub: ele foi selecionado para gerar a Application, nao como aprovacao para executar o upgrade. Em um SNO, seu upgrade reinicia o unico node e interrompe temporariamente ACM, Argo CD, console e aplicacoes hospedadas. Atualize o hub em uma campanha separada.

5. Aprovar o inicio no Argo CD

Revise o diff da Application upgrade-cluster-dev-01. Confirme que o destino e a API do hub e o namespace e cluster-dev-01. Somente entao execute Sync na console Argo CD, ou use a CLI autenticada:

argocd app diff upgrade-cluster-dev-01
argocd app sync upgrade-cluster-dev-01

Esse Sync inicia a operacao. O ApplicationSet nao tem sync automatico. Um estado Synced significa que o manifesto foi aplicado, nao que o upgrade do OpenShift terminou.

O template das Applications declara explicitamente automated.enabled: false, prune: false e selfHeal: false. Adicionar o cluster a lista ou criar a Application pelo ACM nao inicia o upgrade neste fluxo. Ela aguarda o Sync manual no horario escolhido. Se cadastrar outra Application diretamente pelo ACM, mantenha a opcao de sincronizacao automatica desmarcada: esse template nao controla Applications criadas por outros ApplicationSets.

6. Acompanhar e liberar o proximo lote

No hub:

oc get clustercurator -n cluster-dev-01
oc describe clustercurator cluster-dev-01 -n cluster-dev-01
oc get jobs,pods -n cluster-dev-01

No cluster atualizado, valide novamente versao, operators, nodes, MCPs e aplicacoes. Somente depois libere novas entradas e sincronize o proximo lote. Nao selecione varias Applications para Sync se a intencao e atualizar uma de cada vez. Para garantir sequenciamento automatico, e necessario um workflow adicional que espere conclusao e execute verificacoes antes de avancar.

Sync waves ordenam recursos; nao garantem conclusao de upgrades entre clusters. O campo batch e organizacional, nao um controlador de concorrencia.

7. Falhas, repeticoes e limpeza

O controlador pode alterar desiredCuration ao terminar. Isso pode deixar a Application OutOfSync. Nao configure selfHeal nem ressincronize sem revisar: reaplicar desiredCuration: upgrade pode solicitar nova execucao.

Prune automatico esta desativado. O ApplicationSet usa create-update e preserveResourcesOnDeletion: remover um cluster da lista nao cancela uma atualizacao nem remove automaticamente a Application gerada. Arquive e remova recursos de campanhas concluidas somente apos confirmar seu estado.

Reverter um commit nao faz downgrade do OpenShift. Remover o ClusterCurator ou fechar o Argo CD tambem nao desfaz um upgrade em andamento. Em caso de falha, interrompa novos lotes e investigue o cluster afetado.

Retomada do segundo salto no laboratorio

O primeiro salto terminou no OpenShift, mas o Job do curator falhou durante o monitoramento. A existencia do manifesto no Argo nao comprova a execucao. Em 14/11/2026 o canal ainda era stable-4.18, causando VersionNotFound. O canal foi corrigido para stable-4.20 sem solicitar uma nova versao. O admin-ack da 4.20 ja estava registrado; ele nao substitui revisar o uso das APIs removidas.

oc get clusterversion
oc get co
oc adm upgrade
oc -n local-cluster get clustercurator local-cluster -o yaml
oc -n local-cluster get jobs,pods

Somente prossiga se a versao atual estiver Completed, sem atualizacao em andamento, e o destino estiver disponivel com suas condicoes avaliadas. Nao use force nem ignore riscos para contornar a verificacao.

O manifesto no Git agora remove intermediateUpdate e mantem o destino 4.20.46. Publique essa revisao e revise o diff de upgrade-local-cluster. Um Sync pode iniciar a execucao: nao o execute apenas para testar o diff. Se o recurso ainda aponta para um curatorJob inexistente, um novo Sync nao e prova de retomada. Revise a limpeza/recriacao do recurso de campanha com o administrador, depois de confirmar que nenhum Job ou upgrade esta ativo. Nao exclua o ManagedCluster, o namespace local-cluster ou o ClusterVersion.

Aprovacao manual continua obrigatoria. Acompanhe as conditions do ClusterCurator e o history do ClusterVersion, nao somente Synced no Argo.

8. Ambientes sem internet

Este exemplo assume imagens acessiveis e uma versao anunciada ao cluster. Em uma rede air-gapped, prepare antes o registry espelho, as imagens de release, autenticacao, CA, configuracao de mirrors e OpenShift Update Service interno quando usado. O ACM nao transfere automaticamente as imagens de release.
